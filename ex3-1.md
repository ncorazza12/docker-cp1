## Manifesto final (pod-store-api.yaml)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: store-api
  namespace: store-dev
  labels:
    app: store-api
    tier: backend
    env: dev
spec:
  containers:
    - name: store-api
      image: store-api:1.0
      imagePullPolicy: IfNotPresent
      ports:
        - name: http
          containerPort: 8000
      env:
        - name: APP_ENV
          value: "dev"
        - name: DB_HOST
          value: "store-db.store-dev.svc.cluster.local"
        - name: POD_NAME
          valueFrom:
            fieldRef:
              fieldPath: metadata.name
        - name: NODE_NAME
          valueFrom:
            fieldRef:
              fieldPath: spec.nodeName
      resources:
        requests:
          cpu: "100m"
          memory: "128Mi"
        limits:
          cpu: "500m"
          memory: "256Mi"
      startupProbe:
        httpGet:
          path: /health
          port: http
        failureThreshold: 30
        periodSeconds: 2
      readinessProbe:
        httpGet:
          path: /ready
          port: http
      livenessProbe:
        httpGet:
          path: /health
          port: http
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
```

## Item (d) — Classe de QoS e justificativa

```powershell
kubectl get pod store-api -n store-dev -o jsonpath="{.status.qosClass}"
```

**Print 8** — QoS Class
![Print 8](./images/ex3-1/Print%208%20Descobrir%20e%20justificar%20a%20QoS.jpeg)

**Resultado**: `Burstable`.

**Justificativa**: a classe `Guaranteed` exige que `requests == limits` para **todos** os recursos (CPU e memória) em **todos** os containers do Pod. Neste manifesto, `requests` (100m CPU / 128Mi memória) é diferente de `limits` (500m CPU / 256Mi memória) — portanto não pode ser `Guaranteed`. Como há requests definidos (não é o caso de `BestEffort`, que exige ausência total de requests/limits), o resultado correto é `Burstable`.

## Item (g) — Tempo máximo até o Kubernetes matar o container em caso de falha de liveness

**Fórmula**: `initialDelaySeconds + failureThreshold × periodSeconds`

Como a `livenessProbe` deste manifesto não define `initialDelaySeconds`, `failureThreshold` nem `periodSeconds` explicitamente, valem os defaults do Kubernetes: `initialDelaySeconds: 0`, `failureThreshold: 3`, `periodSeconds: 10`.

Cálculo: 0 + 3 × 10 = **30 segundos**, contados a partir do momento em que a liveness passa a atuar.

Importante: a `livenessProbe` só começa a rodar depois que a `startupProbe` for satisfeita (até 30 × 2 = 60s no pior caso). Ou seja, o tempo total desde o start do container até uma eventual morte por falha contínua de liveness pode chegar a até 60s (startup) + 30s (liveness) = 90s no cenário mais extremo, mas o cálculo específico pedido pelo item (fórmula sobre a liveness) resulta em 30s.
