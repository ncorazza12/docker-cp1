## Passo 2 — Os três Services

**svc-clusterip.yaml**:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: store-api
  namespace: store-dev
spec:
  type: ClusterIP
  selector:
    app: store-api
  ports:
    - port: 80
      targetPort: http
```

**svc-nodeport.yaml**:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: store-api-np
  namespace: store-dev
spec:
  type: NodePort
  selector:
    app: store-api
  ports:
    - port: 80
      targetPort: http
      nodePort: 30081
```

**svc-headless.yaml**:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: store-api-hl
  namespace: store-dev
spec:
  clusterIP: None
  selector:
    app: store-api
  ports:
    - port: 8000
      targetPort: http
```

```powershell
kubectl apply -f D:\k8s-exercicios\svc-clusterip.yaml
kubectl apply -f D:\k8s-exercicios\svc-nodeport.yaml
kubectl apply -f D:\k8s-exercicios\svc-headless.yaml
```

**Diferença entre Endpoints e EndpointSlice (2 linhas)**: `Endpoints` é o objeto legado, um único objeto por Service que lista todos os IPs — não escala bem em clusters grandes com muitos endpoints. `EndpointSlice` é o substituto moderno, particiona os endpoints em fatias (por padrão até 100 por slice), suporta múltiplas famílias de IP/protocolos e é o que o `kube-proxy` e o CoreDNS efetivamente consultam hoje.

**Print 5** — as três saídas de nslookup
![Print 5](./images/ex3-2/Print%205%20as%20tr%C3%AAs%20sa%C3%ADdas%20de%20nslookup.jpeg)

**Explicação**: `store-api` (ClusterIP) e `store-api-np` (NodePort) resolvem para **1 único endereço** — o IP virtual estável do Service, atribuído e balanceado via iptables/`kube-proxy`. Já `store-api-hl` (headless, `clusterIP: None`) não possui IP virtual — o DNS devolve **diretamente os 3 IPs dos Pods** (3 registros `Address:`), pois não existe proxy intermediário: a resolução de nome já é o próprio mecanismo de descoberta e balanceamento nesse modelo.

## Item (f) — Cross-namespace: nome curto falha, FQDN funciona

```powershell
kubectl create namespace store-prod
kubectl run tester2 --image=busybox:1.36 -it --rm --restart=Never -n store-prod -- sh
```

Dentro do shell:
```sh
wget -qO- http://store-api/health
wget -qO- http://store-api.store-dev.svc.cluster.local/health
```

**Print 8** — primeiro comando falhando, segundo funcionando
![Print 8](./images/ex3-2/Print%208%20primeiro%20comando%20falhando%20(timeoutDNS%20not%20found)%2C%20segundo%20funcionando.jpeg)

**Explicação sobre o `search` do `/etc/resolv.conf`**: o `/etc/resolv.conf` de um Pod contém uma diretiva `search` com os sufixos referentes ao **próprio namespace** do Pod (ex.: `store-prod.svc.cluster.local`, `svc.cluster.local`, `cluster.local`). Por isso, o nome curto `store-api` só resolve automaticamente para Services do **mesmo namespace** do Pod cliente. Para acessar um Service em outro namespace, é necessário usar o nome qualificado (`store-api.store-dev`) ou o FQDN completo (`store-api.store-dev.svc.cluster.local`).

## Item (g) — sessionAffinity: ClientIP

`svc-clusterip.yaml` atualizado:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: store-api
  namespace: store-dev
spec:
  type: ClusterIP
  sessionAffinity: ClientIP
  selector:
    app: store-api
  ports:
    - port: 80
      targetPort: http
```

```powershell
kubectl apply -f D:\k8s-exercicios\svc-clusterip.yaml
```

Repetição do teste do item (d):
```sh
for i in $(seq 12); do curl -s http://store-api/; echo; done | sort | uniq -c
```

**Print 9** — todas as 12 respostas vindo do mesmo Pod
![Print 9](./images/ex3-2/Print%209%20agora%20as%2012%20respostas%20devem%20vir%20todas%20do%20mesmo%20hostnamepod%2C%20porque%20o%20sessionAffinity%20ClientIP%20faz%20o%20kube-proxy%20fixar%20as%20requisi%C3%A7%C3%B5es%20de%20um%20mesmo%20IP%20de%20origem%20sempre%20no%20mesmo%20endpoint%20(por%20padr%C3%A3o%2C%20por%20at%C3%A9.jpeg)

Com `sessionAffinity: ClientIP`, o `kube-proxy` fixa as requisições vindas do mesmo IP de origem sempre no mesmo endpoint (por padrão, por até 3 horas — `timeoutSeconds: 10800`), o que explica todas as 12 respostas convergindo para um único Pod.
