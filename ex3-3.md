# Exercício 3.3 — Consertar o manifesto quebrado

**Objetivo**: localizar e corrigir cinco defeitos distintos em manifestos, classificando cada um por tipo de erro.

**Arquivos**: [`quebrado.yaml`](./quebrado.yaml) (original com os 5 defeitos), [`corrigido.yaml`](./corrigido.yaml) (versão final funcional)

---

## quebrado.yaml (versão original, com os 5 defeitos)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: store-api
  namespace: store-dev
  labels:
    app: store-api
     tier: backend
    env: dev
spec:
  containers:
    - name: store-api
      image: store-api:1.0
      ports:
        - name: http
          containerPort: 8000
      livenessprobe:
        httpGet:
          path: /health
          port: 8000
---
apiVersion: extensions/v1beta1
kind: Service
metadata:
  name: store-api
  namespace: store-dev
spec:
  type: ClusterIP
  selector:
    app: store-api
    env: prod
  ports:
    - port: 80
      targetPort: 9000
```

## Progressão incremental de correção

### Defeito (i) — Indentação YAML

```powershell
kubectl apply --dry-run=server -f D:\k8s-exercicios\quebrado.yaml
```

**Print 1** — mensagem de erro do parser YAML
![Print 1](./images/ex3-3/Print%201%20essa%20mensagem%20de%20erro.jpeg)

- **Linha**: `tier: backend` (indentação desalinhada em relação aos demais labels)
- **Tipo**: Sintaxe YAML
- **Sintoma**: falha do parser antes de chegar à validação de schema — erro do tipo "did not find expected key" / "mapping values are not allowed in this context"
- **Comando revelador**: `kubectl apply --dry-run=server`
- **Correção**: realinhar `tier: backend` com os demais labels (`app`, `env`)

### Defeito (ii) — Campo desconhecido (livenessprobe minúsculo)

Após corrigir (i), reexecutando o dry-run:

**Print 2** — correção aplicada (livenessprobe → livenessProbe)
![Print 2](./images/ex3-3/Print%202%20Corre%C3%A7%C3%A3o%20livenessprobe%20%E2%86%92%20livenessProbe%20(camelCase%20correto)%2C%20e%20trocar%20port%208000%20por%20port%20http%20para%20casar%20com%20a%20boa%20pr%C3%A1tica%20do%203.1%20(n%C3%A3o%20%C3%A9%20obrigat%C3%B3rio%2C%20mas%20%C3%A9%20consistente)..jpeg)

- **Linha**: `livenessprobe:`
- **Tipo**: API inválida (campo desconhecido pelo schema)
- **Sintoma**: `ValidationError(Pod.spec.containers[0]): unknown field "livenessprobe"`
- **Comando revelador**: `kubectl apply --dry-run=server`
- **Correção**: `livenessprobe` → `livenessProbe` (camelCase correto); porta referenciada pelo nome (`http`) em vez do número, por consistência com o 3.1

### Defeito (iii) — apiVersion inválida no Service

**Print 3** — correção da apiVersion
![Print 3](./images/ex3-3/Print%203%20Corre%C3%A7%C3%A3o%20apiVersion%20extensionsv1beta1%20%E2%86%92%20apiVersion%20v1%20(Service%20sempre%20foi%20v1%3B%20extensionsv1beta1%20nunca%20existiu%20para%20Service%20%E2%80%94%20esse%20grupo%20era%20usado%20por%20recursos%20antigos%20como%20IngressDeployment%20em%20vers%C3%B5es%20be.jpeg)

- **Linha**: `apiVersion: extensions/v1beta1`
- **Tipo**: API inválida
- **Sintoma**: `error: resource mapping not found for name: "store-api" ... no matches for kind "Service" in version "extensions/v1beta1"`
- **Comando revelador**: `kubectl apply --dry-run=server`
- **Correção**: `apiVersion: v1` (Service sempre pertenceu ao grupo `core/v1`; `extensions/v1beta1` nunca existiu para esse kind e já foi completamente removido do Kubernetes moderno)

**Print 6** — curl travando/timeout
![Print 6](./images/ex3-3/Print%206%20esse%20curl%20deve%20travardar%20timeout%20%E2%80%94%20porque%20nada%20est%C3%A1%20escutando%20na%20porta%209000%20dentro%20do%20container%20(a%20app%20escuta%20em%208000).%20Isso%20%C3%A9%20o%20defeito%20(v)%20nenhum%20erro%20no%20apply%2C%20o%20problema%20s%C3%B3%20aparece%20em%20tempo%20de%20execu%C3%A7.jpeg)

- **Linha**: `targetPort: 9000`

- **Correção**: `targetPort: 9000` → `targetPort: http` (mapeando para a porta 8000, nomeada `http`)

| # | Linha | Tipo | Sintoma | Comando revelador | Correção |
|---|---|---|---|---|---|
| i | `tier: backend` | Sintaxe YAML | Parser falha, "did not find expected key" | `kubectl apply --dry-run=server` | Alinhar indentação com os outros labels |
| ii | `livenessprobe:` | API inválida | ValidationError: unknown field | `kubectl apply --dry-run=server` | Corrigir para `livenessProbe` (camelCase) |
| iii | `apiVersion: extensions/v1beta1` | API inválida | "no matches for kind Service in version..." | `kubectl apply --dry-run=server` | Trocar para `apiVersion: v1` |
| iv | `env: prod` no selector | Incoerente com outro objeto | Endpoints vazio, sem erro no apply | `kubectl get endpoints` | Selector deve casar com os labels reais do Pod |
| v | `targetPort: 9000` | Incoerente com a aplicação | curl trava/timeout | `curl` de dentro de um Pod cliente | `targetPort: http` (8000) |

## Progressão das mensagens de erro (ordem de validação do Kubernetes)

1. **Parser YAML** (defeito i) — falha antes de qualquer contato com a API
2. **Esquema da API** (defeitos ii e iii) — falha na validação de campos/kind conhecidos, ainda em `--dry-run=server`, sem persistir nada
3. **Admission/runtime** (defeito iv) — objeto passa na validação, é persistido, mas o problema (selector sem match) só aparece ao consultar o estado real dos Endpoints
4. **Conectividade** (defeito v) — objeto e Endpoints corretos na estrutura, mas a falha só se manifesta ao tentar efetivamente trafegar dados (porta morta)

Essa sequência mostra a ordem real em que o Kubernetes valida as coisas: sintaxe → schema → estado do cluster (admission/controllers) → comportamento em tempo de execução.

## Pergunta de fechamento (obrigatória)

Os dois defeitos que não geram nenhum erro no `kubectl apply` são o **(iv)** — o `selector` do Service com `env: prod` divergindo do label real do Pod (`env: dev`) — e o **(v)** — o `targetPort: 9000` apontando para uma porta onde nenhum processo escuta. Em ambos os casos, o objeto é sintaticamente válido e respeita integralmente o schema da API, então tanto o `kubectl apply` quanto o `--dry-run=server` o aceitam sem qualquer reclamação. O problema só se manifesta em tempo de execução: no primeiro caso, o `Endpoints`/`EndpointSlice` fica vazio porque nenhum Pod satisfaz o selector definido; no segundo, a conexão de rede chega até o Pod correto, mas cai numa porta onde não há processo escutando, resultando em timeout. Isso ensina que o `apply` — mesmo em modo `--dry-run=server` — garante apenas conformidade **estrutural e de schema**, nunca a correção **semântica** das referências entre objetos (selectors, nomes de porta, valores coerentes com a aplicação real). Por isso, validar um deploy no Kubernetes de forma confiável exige sempre um segundo nível de checagem, com `kubectl get endpoints`, `describe` e testes de conectividade reais — nunca apenas confiar que "o apply passou sem erro" significa "está funcionando".
