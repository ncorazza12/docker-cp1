# Exercício 3.4 — Desafio: Pod multi-container com initContainer, sidecar e emptyDir

**Objetivo**: construir um Pod com um `initContainer` que prepara configuração, um container principal e um container sidecar de logs, todos compartilhando um volume `emptyDir`.

**Arquivo**: [`pod-store-api-full.yaml`](./pod-store-api-full.yaml)

---

## Manifesto (pod-store-api-full.yaml)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: store-api-full
  namespace: store-dev
  labels:
    app: store-api
    tier: backend
    env: dev
spec:
  volumes:
    - name: shared-data
      emptyDir: {}

  initContainers:
    - name: init-config
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          echo "Gerando configuração inicial..."
          echo "APP_ENV=dev" > /data/config.txt
          echo "INIT_TIMESTAMP=$(date)" >> /data/config.txt
          echo "Config criada com sucesso"
          cat /data/config.txt
      volumeMounts:
        - name: shared-data
          mountPath: /data
      resources:
        requests:
          cpu: "50m"
          memory: "32Mi"
        limits:
          cpu: "100m"
          memory: "64Mi"

  containers:
    - name: store-api
      image: store-api:1.0
      imagePullPolicy: IfNotPresent
      ports:
        - name: http
          containerPort: 8000
      volumeMounts:
        - name: shared-data
          mountPath: /data
      resources:
        requests:
          cpu: "100m"
          memory: "128Mi"
        limits:
          cpu: "500m"
          memory: "256Mi"
      readinessProbe:
        httpGet:
          path: /ready
          port: http
      livenessProbe:
        httpGet:
          path: /health
          port: http

    - name: log-sidecar
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          echo "Sidecar iniciado, monitorando /data/config.txt"
          while true; do
            echo "[sidecar] $(date) - conteudo atual:"
            cat /data/config.txt
            sleep 15
          done
      volumeMounts:
        - name: shared-data
          mountPath: /data
      resources:
        requests:
          cpu: "50m"
          memory: "32Mi"
        limits:
          cpu: "100m"
          memory: "64Mi"
```

Total de recursos do Pod: request 200m CPU / 192Mi memória, limit 700m CPU / 384Mi memória — dentro do orçamento de 1 vCPU / 1GB definido para a máquina local.

## Pergunta de fechamento

**Por que o Kubernetes garante que o initContainer termina completamente antes de qualquer container principal iniciar, e o que aconteceria com o conteúdo do emptyDir se o Pod inteiro fosse deletado e recriado?**

O kubelet executa os `initContainers` de forma estritamente sequencial, e cada um precisa terminar com sucesso (`exit 0`) antes que o próximo `initContainer` — ou, ao final, os containers principais — sejam iniciados. Essa é uma garantia do próprio kubelet, útil justamente para preparar pré-condições (geração de configuração, migrações de banco, espera por dependências externas) de forma confiável antes da aplicação subir, evitando condições de corrida.

Já o volume `emptyDir` tem seu ciclo de vida atrelado ao **Pod**, não a um container individual: ele sobrevive a reinícios de containers dentro do mesmo Pod (por isso os dados escritos pelo `init-config`, que já terminou, continuam acessíveis por `store-api` e `log-sidecar`). Porém, se o **Pod inteiro** for deletado e recriado (ou reagendado para outro nó), o `emptyDir` é **destruído permanentemente** junto com o Pod antigo, e o novo Pod recebe um `emptyDir` totalmente vazio — não se trata de armazenamento persistente, e por isso não deve ser usado para dados que precisem sobreviver além do ciclo de vida do Pod.
